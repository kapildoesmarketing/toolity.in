Toolity.in — SEO Audit
======================
Date: 20 Oct 2026 · Commit: f8974d0 · Host: GitHub Pages (static, no server headers/redirect control)
Scope: all 188 pages on disk (183 indexable + 4 noindexed widget embeds + 404), static HTML as a crawler fetches it,
plus rendered DOM via headless Chrome where JS matters. External guidance referenced: Google Search Central
(JavaScript SEO, sitemaps, SoftwareApplication structured data), Open Graph / platform card requirements,
web.dev Core Web Vitals. Numbers below come from scripts, not estimates.

Method
------
1. Static sweep (python, every index.html): title, description, canonical, robots meta, H1, JSON-LD types + parse,
   og/twitter tags, word count inside <main>, <a href> count, image attributes, sitemap membership.
2. Rendered vs static comparison (headless Chrome, --dump-dom) on / and a tool page.
3. Payload inspection: main.css / main.js raw + gzip, third-party scripts, fonts, icon runtime.
4. Manual review of robots.txt, sitemap.xml, llms.txt, deploy workflow, hub pages, blog, home.

Findings (ordered by impact × reach)
------------------------------------

F1  [high · every page]  Site navigation and footer exist only after JavaScript runs
    header.html / footer.html are fetched by main.js (data-include) and injected client-side. In the HTML a crawler
    downloads, a tool page has 2 internal links and the home page has 1 (the logo). After rendering: 50 and 47.
    Why it matters:
      - Googlebot does render JS, but rendering is a separate, deferred queue; link discovery and PageRank flow from
        the raw HTML happen first. 183 pages whose only static links are breadcrumbs = a very shallow link graph.
      - Bing, DuckDuckGo, and essentially all AI crawlers (GPTBot, ClaudeBot, PerplexityBot, Applebot-Extended) do
        NOT execute JS. To them the footer "Popular tools" block and the nav don't exist, and /tools/ is empty.
      - The hub pages (/media/ 68 links, /labs/ 32…) are static and carry the site today. Everything else leans on them.
    Fix (keeps the single-source-of-truth you have now): inline the partials at build time.
      The deploy workflow already runs on push; add one step before upload that replaces
      <div data-include="/components/header.html"></div> with the file contents (sed/python, ~15 lines), same for
      footer and tool-cta. main.js's include loader stays as a no-op fallback for local dev. Zero runtime change,
      ~2 KB more HTML per page, +45 crawlable links per page.
      Alternative if you'd rather not touch the workflow: a wire step that bakes them into the 190 files (rule 54).

F1b [high · /tools/]  The A–Z index renders from the JS registry
    Already noted in the code comment ("ceiling"). It is the one page that links to all 160 tools and it ships with
    2 links + a <noscript> pointing at sitemap.xml. Bake the list at build time from REGISTRY (same step as F1,
    node -e script, ~20 lines); keep the JS filter on top of the baked list.

F2  [high · every share]  og:image is an SVG
    /assets/og-image.svg (1.2 KB, 1200×630) on 171 pages. Facebook, LinkedIn, WhatsApp, X, Slack, iMessage do not
    render SVG previews — shares show no image. twitter:card=summary_large_image then falls back to a blank card.
    Fix: export a 1200×630 PNG (or JPG < 300 KB) once, swap the 171 references, add og:image:width/height and
    og:image:alt. Better: per-tool PNGs are overkill for 160 tools — one brand card + the tool name is fine;
    if you want per-tool cards later, the existing OG Image Generator tool can batch them.

F3  [medium · 147 pages]  Meta descriptions too long
    166–282 chars; SERPs cut at ~155–160 so the call-to-action tail ("…files never leave your device") is lost on
    most. Fix: trim to ≤155 with the privacy hook in the first sentence. A script can flag length; wording is manual.
    Low priority vs F1/F2 — Google rewrites descriptions ~70% of the time anyway.

F4  [medium · every page]  Core Web Vitals risk from shared payload + third parties
    Every page loads: GTM (sync in <head>, then its container), iconify-icon runtime from code.iconify.design
    (defer, but icons pop in → CLS on 8–30 icons per page), Google Fonts CSS (render-blocking, 5 weights),
    main.css 129 KB raw / 25 KB gz, main.js 96 KB / 24 KB gz. The header is injected after load → the fixed header
    and page content shift once (CLS) unless the placeholder reserves height.
    Concrete, cheap wins:
      a. Reserve header height: [data-include*="header"] { min-height: var(--header-height) } (1 line, kills the shift).
      b. Self-host Inter as 2 variable-font woff2 files + <link rel=preload as=font>; drop 300 weight if unused.
         Removes a third-party DNS+TLS round-trip from the critical path.
      c. Icons: 2058 of 2062 uses are lucide. Inline an SVG sprite for the ~40 icons the header/footer/templates use
         and keep iconify only for tool bodies — or set width/height on <iconify-icon> (already done) + a CSS
         `iconify-icon { display:inline-block; width:1em; height:1em }` fallback so empty custom elements reserve space.
      d. GTM: move the snippet to after <body> start or load it on first interaction/idle. Measure first — it's the
         single largest third-party cost.
    Verify with PageSpeed Insights on 3 URLs (/, /media/image-compressor/, /games/2048/) before and after.
    GitHub Pages already serves gzip/brotli and long cache for hashed URLs; the ?v= scheme is fine.

F5  [medium · 24 pages]  Structured data gaps
    - Home: Organization only. Add WebSite with potentialAction SearchAction (target https://toolity.in/tools/?q={q}
      — the A–Z filter already reads the query; wire it to read ?q= as well, 2 lines) and sameAs for the socials.
    - 7 hub pages (/media/ /docs/ /labs/ /dev/ /data/ /games/ /widgets/) and /tools/: add CollectionPage +
      ItemList of the tools on the page, and BreadcrumbList. The hubs are your strongest pages; give them schema.
    - WebApplication on tools: valid, but Google's software rich result needs aggregateRating or review — you don't
      have ratings, so no rich result today; that's fine and honest. Don't fabricate ratings.
    - FAQPage: Google now shows FAQ rich results only for authoritative gov/health sites; keep the markup (it still
      helps understanding and AI answers) but don't expect SERP accordions.

F6  [low · sitemap]  lastmod is bulk-stamped
    58 URLs 2026-10-05, 29 on 10-06, 20 on 10-18 … Google uses lastmod only if it is consistently truthful and
    ignores priority/changefreq. Fix: generate lastmod from `git log -1 --format=%cI -- <dir>/index.html` in the
    wire scripts (one-liner per URL). No change in rank, but faster recrawl of pages you actually changed.

F7  [low · 1 page]  /blog/ is a placeholder that is indexed
    "Post title", 88 words, in sitemap, Blog schema. Either publish the first post or add
    <meta name="robots" content="noindex,follow"> and drop it from the sitemap until there is content.
    Footer links to it from every page, so it also leaks a little link equity to nothing.

F8  [low · cosmetic]  Titles for legal/company pages are short (18–29ch) and mix two separators
    "— Toolity.in" on 5 pages, "| Toolity" on 182. Normalise to "| Toolity"; short is fine for legal pages.

F9  [info]  Things that are already right and worth keeping
    - URL structure: /category/tool/, trailing slash, lowercase, no params. CNAME + HTTPS.
    - 404 is noindex; embeds are noindex + canonical to parent; /templates/ disallowed.
    - One H1, keyword-first titles, breadcrumbs with schema, FAQ sections with real content (median 411 words).
    - llms.txt + WebMCP + security.txt + explicit "credit as Done with Toolity.in" — unusually good agent readiness.
    - Images have alt/width/height; logo preloaded as webp.
    - responsive-check.js, lint-tools.sh, a11y-check.sh — a check culture already exists; an seo-check fits in.
